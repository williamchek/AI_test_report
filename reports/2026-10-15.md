## ✍️ Tech article deep-dives

### "Are Harnesses Worth the Cost?" — when guardrails help coding agents, and when they just burn money

- **Source**: Martin Fowler's site, 2026-10-13. Read in full: https://martinfowler.com/articles/are-harnesses-worth-the-cost.html
- **Core argument**: A "behavioral harness" is guardrails plus live feedback for a coding agent — *guides* (API specs, examples, skills) that steer it before it acts, and *sensors* (contract tests, mocks) that report back after. The author ran a controlled experiment: Codex building the same backend service, 10 runs with and without the harness, judged by 178 acceptance tests it never saw during development.
  1. **Frontier model (GPT-6 Sol)**: the harness used **10.5× the tokens, ~3× the time, ~7× the cost** ($2.68 vs $0.41) — and both conditions passed 10/10. No benefit detected.
  2. **Cheap model (GPT-6 Luna)**: unharnessed 3/10 → harnessed **10/10**, at $0.27 per run — still cheaper than unharnessed Sol ($0.41).
  3. **The takeaway**: build harnesses to make *small* models reliable, not to babysit big ones. The author frames the mechanism as "executable attention": the harness pulls dropped requirements back into focus whenever a check goes red.
- **Why it matters** (plain version): if you pay for an AI coding assistant, the expensive question isn't "which model is smartest" but "which model, with how much supervision, delivers reliable results cheapest." This is the first experiment I've seen that puts real numbers on that trade-off.
- **My take**: the framing is genuinely useful, with three caveats. (1) Small sample — 10 runs, one task, one unusually detailed brief; the author says so himself. (2) The economics exclude the cost of *building* the harness (writing contracts, examples, mocks) — the unmeasured part that decides whether the math works for your team. (3) The most practical variant — sensors as a final gate only, for frontier models — wasn't tested; that's his stated next experiment. Read it for the decision framework, not the exact dollar figures.

## 🛠️ Agent skill tests

### `brand-voice-guidelines` (claudia-skills) — turn posts you like into a voice guide your agent can actually follow ⭐4.5/5

- **What it is**: A skill (a step-by-step playbook for AI agents) that derives a voice guide from posts that already sound right: measure them with a script (length, emoji, signature words, openers), read them for traits, write do/don't pairs with real lines, encode the checkable rules in JSON, and lint every draft before a human approves it. MIT, from the 104-skill claudia-skills collection (v2.0).
- **Newcomer translation**: instead of telling an AI "write in a warm tone" (which means ten different things), this method studies examples of writing you like, writes down the concrete patterns, then automatically checks each new draft against them.
- **How I tested it**:
  - Read `SKILL.md` and the voice-extraction reference in full.
  - Ran `node scripts/voice-check.mjs stats` on the two published AI Test Report editions. It fingerprinted 6 sections (median 1,787 chars, 83% use emoji, signature words: agents/test/code/install/verified) with an honest **"only 6 posts; 30+ gives a steadier fingerprint"** warning.
  - **Disclosed deviation**: the full method wants 30–100 posts plus an owner blind test; with 2 editions in existence, I wrote a one-page voice guide from the fingerprint plus the owner's editorial direction (accessible and resource-oriented, for learners — not just veterans) — and used it to write **this very edition**, including a never-lines list (no "revolutionary", no "seamless", no "delve").
  - Ran the lint on the finished draft's sections: no FAILs — 2 sections PASS, 3 CHECK with emoji-set nits only. Two nits were legitimate (I used 🖐️ and ✨, which weren't in my rules yet — the guide evolves); the rest were a script quirk (it strips Unicode variation selectors when extracting emoji but not when comparing, so ✍️ reads as ✍). No banned phrases, no length violations. Per the skill's own rule — "if the lint flags your own good writing, the rule is wrong, not the writing" — the variant-selector comparison is the bug, not the draft.
- **Verdict & score**: ⭐4.5/5. The measure → guide → lint loop is concrete, and I felt the difference writing today — the never-lines list alone is worth adopting. Half a star off: the corpus-size assumption doesn't fit young publications, and the blind-test calibration step needs a human in the loop.
- **Who it's for**: Anyone whose AI drafts "don't sound like us" but nobody can say why; teams onboarding AI writing help; newsletter/blog writers who want consistency without hand-holding every draft.
- **Link**: https://github.com/claudia-onchain/claudia-skills (skill: `skills/grow/brand-voice-guidelines`)

## 🔌 MCP tests

### trip-agent-mcp v0.1.1 — a local-first MCP server that finds the gaps in your trip and exports a calendar file ⭐4/5

- **What it is**: An MCP server (a plug-in that gives an AI assistant new tools) for trip planning. Your assistant assembles a trip from your booking emails; this server checks it for gaps by plain rules — a night with nowhere to stay, a journey that doesn't connect, a missing return — and exports it as a `.ics` calendar file with the gaps marked as placeholders. No database, no account, no API key. Early software, v0.1.1.
- **Newcomer translation**: you tell your AI about your flights and hotel; this tool double-checks "wait, where do you sleep on December 5th?" and puts everything on your calendar.
- **How I tested it**:
  - `npm pack trip-agent-mcp` + install (95 packages). Spoke raw stdio JSON-RPC with a hand-written Node client: `initialize` ✓, `tools/list` ✓ — my first guessed tool names (`trip_init`, `trip_add_flight`) were wrong; the real 4 are `export_trip`, `check_trip`, `get_trip_file_info`, `open_trip_file`. (Read the schema first — lesson re-learned.)
  - Built a Tokyo trip with a **deliberate gap** (hotel checkout Dec 5, flight home Dec 6): `check_trip` found the unbooked night ✓ — plus 3 more flags, two of which are literal string mismatches (HND ≠ "Tokyo", TPE ≠ "Taipei") rather than real problems. Honest false-positive note: the rule engine matches place names as strings.
  - `export_trip` wrote an `.ics` with **11 events**: flights, airport check-in blocks, hotel stay, included breakfasts, and 4 "Missing:" placeholder events with stable UIDs (re-importing updates instead of duplicating).
  - **Privacy check**: booking codes in the file were shortened to their last characters ("code ending 6") — full codes never leak, as the README promises. Test file cleaned up afterwards.
- **Verdict & score**: ⭐4/5. The core loop (check gaps → export calendar) genuinely works and the privacy design is thoughtful. One star off: early software (the README says so), strict string matching causes false positives, and it writes to a fixed `~/Documents/trip-agent` folder — my `outDir` argument was silently ignored.
- **Who it's for**: Travelers who plan with an AI assistant and want a second pair of eyes on the itinerary; privacy-conscious folks who like that everything stays on their own machine.
- **Link**: https://github.com/yamhochi/trip-agent-mcp · npm `trip-agent-mcp`
