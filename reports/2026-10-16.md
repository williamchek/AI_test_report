## 🆕 Open-source project tests

### jevgrep: ask your code questions in plain English instead of matching words ⭐3/5

![Terminal: jevgrep installs in 8s, lists 209 files, then refuses every search without an API key](https://drive.google.com/thumbnail?id=1tNuGctYuz1n_0fDj1VGtZ5DZr9IzJQv2&sz=w2000)

- **In one sentence**: A command-line tool (TypeScript, needs Node.js 22+) that lets a coding agent find code by asking "where is caching implemented" instead of running keyword searches, using a judge model (an AI model that classifies and picks) to rank files by meaning.
- **Why it caught my eye**: Created 2026-09-26, already ~2,670 stars, MIT; the README ships its own SWE-bench comparison (8/10 tasks done, ~30% cheaper) and a self-installing agent skill (a step-by-step playbook for AI coding agents): unusually testable claims for a week-old project.
- **I tried it**:
  - `npm install -g @dzhng/jevgrep`: 3 packages, 8 seconds, v0.8.0. Clean.
  - `jg files` on its own repo: 209 files eligible (6.4 MiB), zero provider requests made, hidden and protected paths skipped by default. The offline plumbing works.
  - `jg skill --yes --agent claude-code --global`: cloned its repo and installed the skill cleanly ("Selected 1 skill: jevgrep").
  - What surprised me: the README's whole pitch is semantic search, yet without a provider key both `jg doctor` and a real query die with the same one-liner: "Run jg auth...". The tool installs in seconds and then locks its only feature.
- **The catch**: the one thing it exists to do needs a paid provider key (Vercel AI Gateway, TypeSafe, OpenRouter, OpenCode Zen, or a compatible endpoint); I had none, so the semantic search itself is untested and the SWE-bench numbers (8/10, ~30% cheaper) are the README's claims, not mine. Offline it buys you nothing a file lister wouldn't.
- **Try it if**: you're a developer whose agent keeps grep-spamming (grep is a tool that searches files for text) your repo, and you have an LLM (an AI model you call over an API) key to spare.
- **Skip it if**: you have no API key, or you just want a better grep: the offline parts give you nothing new.
- **Score**: ⭐3/5: installs and wires up cleanly, but the central claim sits behind a key I couldn't test; watch, don't adopt yet.
- **Link**: https://github.com/dzhng/jevgrep

## ✍️ Tech article deep-dives

### "The code I never wrote": "70% vs 90%" is meaningless until you say where you draw the line

- **Read this if**: you've ever quoted (or been quoted) a number like "AI writes 70% of our code" and felt it meant nothing, or you feel uneasy about shipping code you didn't write.
- **The argument in 3 bullets**:
  - The percentages are empty until you say where you draw the line. His manager's 70% (share of development work) and his 90% (lines landing in files) can both be true; they count different things, and he admits he never measured his number.
  - The line has moved at every abstraction layer (each new layer that hides the one below): machine code to BASIC (a simple 1980s programming language) on his Amstrad CPC 464 (a 1980s home computer), BASIC to Delphi (a 1990s visual programming tool), frameworks like Symfony (a popular PHP web framework), and now natural language via coding agents. Each time, programmers first stopped writing a layer, then stopped reading it.
  - The real question is not "how much does the agent write" but when a layer you no longer read stops being a bet. He trusts compilers because millions use them and failures get fixed for everyone; an agent's output is a one-off bet he can only trust after checking it often enough. DHH (David Heinemeier Hansson, creator of Ruby on Rails) already doesn't read his agents' Rust; the author hasn't decided about his PHP yet.
- **Why it matters to you**: the next time a vendor, manager, or keynote quotes an AI-coding percentage, you'll ask the one question that deflates it: what exactly did you count.
- **My take**: the taxi-driver analogy (a driver's job is the route, the surprises, and the responsibility, not burning fuel) is the essay's sharpest point, and his admission that the 90% was never measured is what makes the argument credible. The cold water: DHH not reading generated Rust is one data point from a confident veteran, and Simon Willison (a well-known programming writer) admits he's uneasy about not reviewing agent output for a reason; neither settles the trust question for teams without 25 years of experience.
- **Link**: https://dev.to/shagshag/the-code-i-never-wrote-3adg

- **Why it caught my eye**: Created 2026-10-07, already 804 stars and 84 forks, MIT, no sign-up, no API key; the four Python tools run on the standard library (Python's built-in modules, nothing to install), so the whole deterministic half is testable on any machine.

- **Try it if**: you're a curious non-founder who wants to sanity-check a business idea with real arithmetic before spending a dollar.
- **Skip it if**: you want the debates and panels but don't run an AI coding agent; the math tools alone are half the pack.

## 🔌 MCP tests

### fetch server v1.0.0: the official fetch server finally refuses internal addresses, and I watched it do it ⭐4/5

![Terminal: fetch MCP v1.0.0 blocks 127.0.0.1 with a named error, then fetches it fine with --allow-private-ips](https://drive.google.com/thumbnail?id=1DBCBnVFiWOzWSu5ZdAwIkqqlzN_zOO-y&sz=w2000)

- **In one sentence**: The reference MCP (a standard that lets AI assistants use external tools) fetch server hit v1.0.0 (Python side uses CalVer, version numbers that are calendar dates: 2026.10.10) on 2026-10-11 with a real security fix: it now refuses loopback (your own machine), private-network, and cloud-metadata addresses on every request, including redirect hops.
- **Why it caught my eye**: the fix closes a genuine SSRF hole (a trick where a model-supplied URL makes the server call internal addresses): the exact bug that bites when agents fetch URLs on your behalf: and the release notes describe a before/after behavior I could actually reproduce.
- **I tried it**:
  - Spoke raw JSON-RPC (a strict request/response message format) over stdio (standard input/output, how the server talks to clients) to `uvx mcp-server-fetch`: `initialize` reported `mcp-fetch 2026.10.10`, `tools/list` exposed one tool, `fetch`.
  - Fetched my own test page at `http://127.0.0.1:8471`: refused, naming the address and the escape hatch ("Start the server with --allow-private-ips to allow private, loopback and link-local addresses").
  - What surprised me: restarted with `--allow-private-ips --ignore-robots-txt`, the same URL fetched fine and returned my page byte-for-byte. The guard is one flag deep, no restart dance.
  - Read the source: the refusal is a request hook that httpx (a Python library for making web requests) runs before every request, so a public URL can't redirect-hop to an internal one. That part I verified by code reading, not a live redirect test.
- **The catch**: under this VM's normal proxy environment, every fetch dies with `Invalid port: ':1]'`: httpx 0.28.1 chokes on the bracketed IPv6 entries (`[::1]`) in NO_PROXY (the list of addresses that skip the proxy). I confirmed it with a bare `httpx.AsyncClient(proxy=None)` raising the same error. In proxy-heavy sandboxes the server is unusable until that dependency bug is fixed, and the new guard can't even run there.
- **Try it if**: you run an MCP host and want the reference fetch server with the private-address guard on by default.
- **Skip it if**: your environment sets NO_PROXY with bracketed IPv6 entries, where the current dependency stack breaks every fetch.
- **Score**: ⭐4/5: the security fix does exactly what the release notes say; one star off for the dependency bug that breaks it in proxied environments.
- **Link**: https://github.com/modelcontextprotocol/servers · release notes: https://whatsnew.fyi/product/servers/releases/v1.0.0
