# AI 審查員「省 token」的承諾：同一份程式碼，它花了 30 倍，抓到一樣的 bug

一台 16GB 的 Mac mini、一個 52,000 顆星的審查工具，和一場關於「省下的 token 去哪了」的追問

一名開發者在社群平台上貼出截圖，說他把一份程式碼變更丟給 AI 審查工具，工具回傳了四則留言，其中兩則抓到了真正的 bug。底下有人問：那跟直接問模型有什麼不一樣？

把程式碼交給 AI 審，省的是時間，還是換個地方花掉？

## 從一次 53 行的審查說起

open-code-review 是阿里巴巴開源的 AI 程式碼審查工具，命令列程式 `ocr`，GitHub 上有 52,132 顆星。它的賣點寫得很具體：同一份程式碼，它比 Claude Code 更準、誤報更少，用的 token 只有大約九分之一，驗證基礎是 200 個真實 PR、橫跨 50 個儲存庫。這些數字是廠商的主張，尚未見獨立查證，閱讀時宜留意。

我把這個承諾拿到一台 16GB 的 Mac mini M4 上驗證。模型是 qwen3:8b，一個 5.2GB 的開源小模型，跑在原生的 Ollama 上，沒有接任何付費 API，也沒有金鑰。測試方法很直接：先寫一個小專案，埋三個程式審查應該抓到的 bug——一個空值 dereference、一個 XSS、一個 check-then-act 的 race condition——再加一個乾淨檔案當對照，然後叫工具審查那份 53 行的變更。

結果是 2/3。XSS 抓到了，行號正確，列為 critical；空值問題抓到了，行號正確，列為 high。Race 沒抓到，工具只在那幾行下面留了一則「加 try/catch」的建議，真正的 double-booking 問題一個字也沒提。乾淨檔案 0 誤報。整份審查跑了 10 分 3 秒，工具回報用了約 41,257 個 token。

這個結果有兩個地方值得停下來看。第一，工具的規則本身就沒有 race 這一條。它的審查規格書有 50 行，Async 那一節只談錯誤處理、偏好 async/await 和迴圈裡用 Promise.all——而 Promise.all 的建議如果照做，會讓重複訂位更容易發生，不是更難。換句話說，工具在這個 bug 上不只是沒看到，它的建議還往反方向走。

第二，小模型叫工具的過程並不順。qwen3:8b 在這次審查裡有三次吐不出可解析的工具呼叫，工具重試後才救回來。同一種失敗在後面每一輪測試都出現，Python 審查三次、大 diff 三次、掃描四次。這屬於實測觀察，不是推論：小模型驅動這套工具，工具呼叫本身就是一個不穩定的環節。

但也要先肯定它做對的部分。有一則留言一開始被放錯了檔案，工具的定位模組把它重新歸位到正確的檔案和行號——那道「把關」是真的在運作。檔案挑選也完全正確，三個變更檔案一個不少，README 被正確排除。這些是工具宣稱的「確定性工程」，本次實測中它確實兌現了。

## 「1/9 token」：承諾與對照

廠商的數字要怎麼驗？它對照的是 Claude Code，但這台機器上沒有 Claude Code，也沒有付費金鑰可以跑對照組。所以我換了一個對照：同一個模型、同一份 diff、直接下一句「幫我審這份變更」——沒有規則、沒有定位、沒有多輪審查，純粹叫模型自己看。

對照組的結果是 2/3，抓到同樣的 XSS 和空值問題（行號各差一行），race 一樣沒抓到，誤報 2 則。時間 35.9 秒，token 1,352 個。

把兩邊並排，承諾的形狀就變了：

| 任務 | 抓到 | 誤報 | 時間 | Token |
|---|---|---|---|---|
| JS diff（53 行），ocr 審查 | 2/3（XSS、空值） | 0 | 10 分 3 秒 | 41,257 |
| JS diff（53 行），直接問模型 | 2/3（XSS、空值） | 2 | 35.9 秒 | 1,352 |
| Python diff（41 行），ocr 審查 | 2/3（SQL 注入、可變預設值） | 0 | 7 分 17 秒 | 25,315 |
| 大 diff（203 行），ocr 審查 | 0/3 | 0 | 15 分 26 秒 | 37,470 |
| 整倉掃描（Python 專案），ocr 掃描 | 2/3（pickle、可變預設值） | 0 | 18 分 12 秒 | 48,711 |

直接問模型用的 token 是 ocr 的三十分之一，時間是十七分之一，抓到的一樣多。這個對照只是同模型、同一份 diff 的一次比較，不是廠商「1/9」的對照——廠商對照的是 Claude Code，那組數字本次沒有條件驗證，尚待獨立查證。但它說明了一件事：在小模型的條件下，ocr 多花的 token 換到的不是更多抓到的 bug，而是更少的誤報（0 則對 2 則）、定位準確的行號留言，和規則與多輪審查的整套流程。

這個推論合理，但要放在比例尺上看。對照組只有一份 diff、一個模型，樣本很小；廠商的基準是 200 個 PR，跑的恐怕是前沿模型，不是 8B 小模型。不能說廠商的數字是錯的，只能說在「本機小模型、沒有金鑰」的條件下，省 token 的承諾沒有兌現——花的反而更多。而它真正省下來的，是誤報。


## 換了語言，換了規模

同一套方法，換成 Python 再跑一次。新的測試專案有四個檔案，埋了三個 bug：SQL 注入、可變預設參數、pickle 反序列化。結果又是 2/3：SQL 注入抓到了，行號正確，建議的修正（參數化查詢）也是對的；可變預設值抓到了，修正建議也是對的；pickle 沒抓到——儘管安全的 JSON 替代寫法就放在同一個檔案裡當對照，工具一個字也沒提。乾淨檔案 0 誤報。7 分 17 秒，約 25,315 個 token。

值得注意的是，兩次漏掉的 bug 都是「最危險的那一個」。JS 那次漏的是 race，Python 這次漏的是 pickle 反序列化——使用者輸入直接餵給 `pickle.loads`，等於開了一扇任意程式碼執行的門。工具抓到的都是 pattern 明確的 bug（XSS、空值、SQL 注入、可變預設值），漏掉的都是需要理解「這段程式碼在做什麼生意」的 bug。這是本次實測的觀察，不是對工具的定論，但兩次測試指向同一個方向。

再把規模放大。七個檔案、203 行的變更，埋了三個 bug：缺少權限檢查、N+1 查詢、折扣重複計算。結果是 0/3，三個全漏，只留下兩則無關的建議——一則說範例資料應該換成安全儲存，一則建議改用非同步加密函式。15 分 26 秒，約 37,470 個 token。

這個推論合理，但要放在比例尺上看：203 行並不是什麼大 PR，日常開發的變更經常比這更大。工具在 53 行時抓得到 2/3，203 行時一個都抓不到——中間沒有過渡，就是直接歸零。更值得留意的是 token 數：203 行的審查用了 37,470 個 token，比 53 行那次的 41,257 還少。成本沒有跟著程式碼量走，花的錢在流程本身，不在程式碼。

**換大模型會不會好一點？** 這個問題本次沒有答案。qwen3:14b 的下載只跑到 10%，速度每秒 2.3MB，預估還要 57 分鐘，我把它停掉了。14B 能不能抓到 race，目前無法下定論——文章不會假裝它能。

## 掃描模式：互補的另一半

ocr 除了審查變更，還有 `scan` 模式：整倉掃描，不只看 diff。同一個 Python 專案，掃描跑了 18 分 12 秒，用了約 48,711 個 token，抓到 2/3——這次抓到的是 pickle 和可變預設值，漏掉的是 SQL 注入，因為負責那個檔案的子任務逾時了。

兩個模式合起來，三個 bug 全抓到了；但任何一個模式單獨上，都只抓到兩個。掃描的代價是審查的約 2.5 倍時間、約 2 倍 token。這個對照是本次實測中最有用的發現之一：兩種模式看的是不同的東西，互補，不是重複。

但掃描有一個更值得注意的毛病：它安靜地失敗。五個檔案的子任務裡有三個逾時報錯——包括裝著 SQL 注入的那個——但整輪掃描最後仍然以成功（exit 0）結束，還附上一份專案摘要。逾時的檔案只是沒有結果，不會有人提醒你它沒看完。摘要本身也出了錯：把 medium 和 low 的問題寫成「兩個 critical」，還把一個函式名稱寫錯（"add_to nad"），並把一則建議列為重點問題——而那則建議的修正程式碼引用了一行檔案裡根本不存在的 `return sum(items)`。

這屬於實測觀察：掃描模式的價值是真的（它抓到了審查漏掉的 pickle），但它的失敗是安靜的。一個沒有報錯、卻少看了一個檔案的掃描，比一個直接報錯的掃描更需要人盯著。

## 16GB Mac 的帳單：資源使用率

這些測試都是在同一台 Mac mini M4 16GB 上跑的，資源數字是實測，不是估計。

模型載入後大約佔 5.0 到 5.8GB 記憶體，掃描那輪最高到 7.3GB；GPU 使用率 100%。審查進行時，整台機器的可用記憶體剩下 16% 到 44%，swap 本來就用了約 4GB，審查一輪再長約 2GB。

審查一份 53 行的變更要 10 分鐘，期間機器的記憶體壓力一直都在——這是本地審查真正的成本，不在 token 帳單上，在時間和機器上。

## 台灣開發者能做什麼

**先拿它當預檢，不要當終審，風險最低。** 它抓得到 pattern 明確的 bug——XSS、空值、SQL 注入、可變預設值——而且在本次測試裡 0 誤報。把審查結果當成「第一輪篩子」，人再看一遍，這個用法是站得住的。不要把它當成「審過就沒問題」的章：race、pickle、權限檢查這類需要理解業務邏輯的 bug，它都漏過。

**再決定要不要接本地模型。** 沒有金鑰也能跑，程式碼不用離開自己的機器——對不能把程式碼送上境外雲的團隊來說，這是真的有價值的理由。但要接受它的代價：一份 53 行的變更 10 分鐘，一份 203 行的變更 15 分鐘還抓不到東西；掃描模式更要 18 分鐘，而且可能安靜地少看一個檔案。時間成本會因機型與模型而異，16GB 的 Mac mini 是這次測試的條件。

**最後才是相信 token 數字。** 廠商的「1/9」是對照 Claude Code 的基準，在沒有自己的對照組之前，宜視為參考。本次測試裡，同一顆模型直接問只用了 1,352 個 token，ocr 用了 41,257 個——多花的 token 買到的是更少的誤報和定位準確的留言，不是更多的 bug。如果你要的是「省」，先算自己那一欄的帳：時間、誤報、還是 token，哪一個對你最貴。

## 觀察：省下的不是 token，是誤報

這個現象的核心，其實不在 token，而在更老的問題：審查工具賣的到底是什麼？

如果賣的是「抓到更多 bug」，本次測試沒有支持這個說法——同一顆模型，直接問和走工具，抓到的一樣多，漏掉的也一樣是 race。如果賣的是「抓到的 bug 更可信」，那就有東西了：0 誤報對 2 誤報，定位準確的行號，一則留言被放錯檔案還會被自動歸位。工具的價值在鷹架，不在眼睛；眼睛是模型的，鷹架才是工具的。

接下來有三件事值得追蹤：換更大的本地模型（14B 或前沿模型）會不會抓到 race；廠商會不會公開那 200 個 PR 基準的對照細節，讓「1/9」可以被獨立查證；以及小模型的工具呼叫穩定性會不會改善——本次每一輪審查都有三次吐不出可解析的呼叫，這個數字比任何一個 bug 都穩定。

至於本地模型審查能不能取代人工審查，還是只是多一道有用的預檢，目前無法下定論。

*說明：本文的測試全部在 2026 年 11 月 18 日進行，機器是 Mac mini M4 16GB，模型是 qwen3:8b（Ollama 0.40.16，實測 19.57 / 19.68 tok/s），工具是 open-code-review v1.13.11（第一輪）與 v1.13.12（重裝後的後續測試）。審查用的測試專案是自寫的，bug 是刻意埋入的，目的是驗證工具抓不抓得到，不是模擬真實 PR。廠商「比 Claude Code 更準、約 1/9 token、200 個 PR、50 個儲存庫」的說法出自廠商自己的基準，未經獨立驗證；本次沒有跑 Claude Code 對照組。qwen3:14b 沒有測到（下載太慢而中止），文中不對它做任何推論。測試過程中 SSH 隧道斷過兩次、工具一度需要重裝，這些是環境問題，不是工具的問題。數字溯源：各輪測試的完整輸出、計分表、截圖與資源採樣記錄都在測試目錄裡，token 數是工具或 API 回報的數字，不是估計。*
